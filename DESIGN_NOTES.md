# Design Notes: LSPU Event Management System

This document outlines the architectural decisions, UI/UX philosophy, and technical implementations that power the LSPU Event Management System.

## 1. System Architecture

The application follows a traditional **Monolithic MVC (Model-View-Controller)** architecture using Flask. 
- **Models:** Handled by SQLAlchemy (SQLite in development). Defines relationships between Users, Events, Registrations, Waitlists, and Expenses.
- **Views:** Rendered using Jinja2 templates. We utilize a base template (`base.html`) and reusable UI macros (`_ui.html`) to ensure consistency.
- **Controllers:** Flask routes (`app.py`) handle business logic, authentication, and data processing.

## 2. UI/UX Philosophy

### Design System
- **Typography:** Uses `DM Sans` for body text (highly readable) and `Manrope` for headings (strong, modern geometric feel).
- **Color Palette:** 
  - **Navy & Deep Blue:** Conveys trust, academia, and institutional stability.
  - **Gold:** Used sparingly as an accent for premium features (featured events, archive highlights).
  - **Warm Paper:** The background isn't pure white; it's a soft `#f8f7f3` to reduce eye strain and give a "printed document" feel.
- **Dark Mode:** Implemented entirely via CSS variables (`--ink`, `--surface`, etc.) and toggled using a `data-theme="dark"` attribute on the `<html>` tag. Preferences are saved in `localStorage`.

### Role-Based Workspaces
Instead of a "one-size-fits-all" dashboard, each role gets a tailored environment:
- **Students:** Focused on discovery. The UI uses large cards, clear capacity meters, and prominent action buttons.
- **Professors:** Focused on data. The UI relies heavily on clean tables, filtering, and Excel export.
- **Admins:** Focused on control. The UI features terminal-style logs, status overrides, and comprehensive CRUD interfaces.

### Responsive Design
- **Desktop:** Utilizes CSS Grid for complex layouts (like the landing page).
- **Mobile:** Tables transform into "stacked" cards using CSS `data-label` pseudo-elements. The navigation collapses gracefully.

## 3. Data Structures & Algorithms (DSA)

To demonstrate core computer science concepts, several custom algorithms are implemented in `services/dsa.py` instead of relying entirely on database defaults.

### Merge Sort (Custom Implementation)
- **Where:** `app.py` (Student event board, Professor attendance list).
- **Why:** We need to sort events by a custom status order (Ongoing -> Not Started -> Ended) and then alphabetically. SQL `ORDER BY` cannot easily handle custom enum sorting. Merge sort guarantees `O(n log n)` time complexity and keeps the sorting logic within the Python layer.
- **Implementation:** `merge_sort(items, key=lambda x: x)` divides the list recursively and merges it back together.

### Binary Search
- **Where:** Student Event Search (`student_home`).
- **Why:** If a student types an exact event title, a linear search `O(n)` is inefficient. Because the events are already sorted, we can use Binary Search `O(log n)` to find an exact match instantly before falling back to a substring search.
- **Implementation:** `binary_search_title(sorted_events, title)`.

### Hash Index (Registration Lookup)
- **Where:** `RegistrationHashIndex` class.
- **Why:** Checking if a student is already registered for an event usually requires a database query. We use a Dictionary (Hash Map) to achieve `O(1)` lookups for `(student_id, event_id)` pairs.

### FIFO Queue (Waitlist Management)
- **Where:** `cancel_registration` route.
- **Why:** When an event is full, students join a waitlist. If a registered student cancels, the *first* person who joined the waitlist must be promoted.
- **Implementation:** Uses Python's `collections.deque` to enforce First-In-First-Out (FIFO) behavior.

## 4. Security Decisions

- **Passwords:** Never stored in plain text. Hashed using `werkzeug.security.generate_password_hash` (PBKDF2 with SHA256).
- **CSRF Protection:** All POST forms include a hidden `csrf_token` generated by Flask-WTF. This prevents Cross-Site Request Forgery.
- **OTP (One-Time Password):** Registration and password resets require a 6-digit OTP sent to the user's email. This prevents spam accounts and verifies email ownership.
- **Role-Based Access Control (RBAC):** A custom `@role_required` decorator wraps routes to ensure a student cannot access admin routes (and vice versa).
- **File Uploads:** Restricted to specific extensions (`.jpg`, `.png`, `.webp`), renamed using `uuid4` to prevent directory traversal or overwrite attacks.

## 5. Database Relationships

- **User -> Registration:** One-to-Many.
- **Event -> Registration:** One-to-Many.
- **Event -> Expense:** One-to-Many.
- **User -> WaitingList:** One-to-Many.
- **Unique Constraints:** A student can only have *one* registration per event (`uq_student_event`).

## 6. Event Status Logic

Event statuses are calculated dynamically via the `Event.status` property:
1. If `archived` is True, return "Archived".
2. If the date has passed, return "Ended".
3. If the date is today, check the time:
   - If current time is past `end_time`, return "Ended".
   - If current time is between `lunch_start` and `lunch_end`, return "Lunch Break".
   - If current time is past `start_time`, return "Ongoing".
   - Otherwise, return "Not started yet".
4. Admins can bypass this logic using `manual_status`.
